# 第 3 章 工具：Agent 的双手

> **本章目标**
> 1. 理解工具（Tool）的本质：一份"说明书"（schema）+ 一个"执行函数"；
> 2. 看懂模型如何"决定"调用工具，以及参数如何传递；
> 3. 理解工具注册、执行、结果回传的完整链路；
> 4. 对照三个代码库，看它们如何定义和调度工具。

## 3.1 生活化开场：一份"岗位说明书"

想象你要给新同事安排一个"查资料"的任务。你不会让他瞎猜，而是给他一份**岗位说明书**：

```
工具名称：查文件
用途：读取指定路径的文件内容
参数说明：
  - path：文件路径（字符串，必填）
  - startLine：从第几行开始读（数字，可选）
  - endLine：读到第几行（数字，可选）
```

模型拿到这份说明书，才知道"哦，我有这个工具可用"。当它觉得需要读文件时，
就会按说明书填参数，输出一段特殊格式的"我要用查文件工具，path=xxx"。

在 Agent 领域，这份"说明书"叫 **工具描述（Tool Schema）**，
"填参数调用"叫 **函数调用（Function Calling / Tool Calling）**。

**一个工具 = 一份说明书（schema）+ 一个执行函数（execute）。** 这是本章最重要的公式。

## 3.2 工具长什么样：三个代码库的真实定义

### dsh 的工具描述（Schema）

dsh 在 `packages/llm/llm/src/types.ts` 定义了 `ToolSchema`，极其简洁：

```ts
// dsh packages/llm/llm/src/types.ts
export interface ToolSchema {
  name: string                 // 工具名
  description: string          // 用途说明（给模型看的）
  parameters: Record<string, unknown>  // 参数定义（JSON Schema）
}
```

就这三个字段。`parameters` 是一个 JSON Schema 对象，描述每个参数的
类型、必填、取值范围。模型正是读这份 schema 来"学会"怎么调用你的工具。

`GenerateOptions.tools` 就是这样一个 schema 数组，随请求一起发给模型：

```ts
tools?: ToolSchema[]  // 模型可见的工具清单
```

### pi 的工具

pi 在 `packages/agent/src/types.ts` 定义了 `AgentTool`，它比 dsh 多了一个
**执行函数**，把"说明书"和"执行"放在一起：

```ts
// pi packages/agent/src/types.ts（节选）
export interface AgentTool<TParameters extends TSchema = TSchema, TDetails = any>
  extends Tool<TParameters> {
  label: string;                                  // 界面显示名
  prepareArguments?: (args: unknown) => TParameters;  // 参数兼容转换（可选）
  execute: (                                  // ← 真正的执行函数
    toolCallId: string,
    params: TParameters,
    signal?: AbortSignal,
    onUpdate?: AgentToolUpdateCallback<TDetails>,
  ) => Promise<AgentToolResult<TDetails>>;
  executionMode?: ToolExecutionMode;          // sequential | parallel
}
```

底层 `Tool`（`packages/ai/src/types.ts`）定义了模型可见的部分：

```ts
export interface Tool<TParameters extends TSchema = TSchema> {
  name: string;
  description: string;
  parameters: TParameters;   // 注意：用 typebox schema，类型安全更强
}
```

pi 的每个具体工具是一个实现 `execute` 的对象。比如 `packages/coding-agent/src/core/tools/`
目录下，就是一个一个工具文件：`read.ts`（读文件）、`write.ts`（写文件）、
`bash.ts`（跑命令）、`grep.ts`（搜索）、`edit.ts`（编辑）……每个文件里
定义了一个 `AgentTool`，有一个清晰的 schema 和一个真正的执行函数。

### codex 的工具：更重的"运行时"

codex 的工具体系最重，由 `ToolSpec`（说明书）+ `CoreToolRuntime`（执行运行时）
组成，注册在 `tools/registry.rs`。它不止"执行函数"，还包含钩子（hooks）、
沙箱、审批、遥测等生产要素。我们第 13 章讲安全时会再看到它。

先记住对照关系：

| 概念 | dsh | pi | codex |
|------|-----|-----|-------|
| 工具说明书 | `ToolSchema` | `Tool`（typebox schema） | `ToolSpec` |
| 工具实现 | 注册进 `ctx.tools` 的服务 | `AgentTool`（含 execute） | `CoreToolRuntime` |
| 模型可见清单 | `GenerateOptions.tools` | `context.tools` | `build_prompt` 组装 |

## 3.3 一次工具调用的完整旅程

现在我们追踪一个工具调用从"模型决定"到"结果回传"的完整生命周期。
假设模型决定调用 `bash` 工具执行 `find . -name "*.ts" | xargs wc -l`。

```mermaid
sequenceDiagram
    participant Model as 大模型
    participant Loop as 推理循环
    participant Tool as bash 工具
    Model->>Loop: 输出 tool-call 块(name=bash, arguments=...)
    Loop->>Loop: 解析 arguments(JSON字符串→对象)
    Loop->>Tool: execute(id, params, signal)
    Tool->>Tool: 运行 shell 命令，收集输出
    Tool-->>Loop: 返回 ToolResult(输出文本)
    Loop->>Loop: 把结果封装成 user 角色消息
    Loop-->>Model: 下次请求带上"工具结果"消息
```

把每一步拆开看：

### 第 1 步：模型输出 tool-call 块

模型在流式输出中，会输出一个结构如下的块（见第 2 章的 JSON 示例）：
`type: "tool-call"`、`id`（本次调用的唯一标识）、`name`（工具名）、
`arguments`（**JSON 字符串**！）。

> 注意：`arguments` 是**字符串**，不是对象。因为模型的输出天然是文本。
> 代码需要再解析一次。dsh 里就有这样一个 `parseArguments` 函数
> （`packages/core/agent-loop/src/tool-calls.ts`）：

```ts
// dsh packages/core/agent-loop/src/tool-calls.ts
/** 解析模型参数：坏的 JSON 保留为文本，空输入映射为 {} */
function parseArguments(raw: string): unknown {
  try {
    return raw ? JSON.parse(raw) : {}
  } catch {
    return raw   // 解析失败就保留原文，交给工具层报错
  }
}
```

注意这里的宽容处理：模型可能输出残缺的 JSON。解析失败时**不直接抛异常**，
而是保留原文，让下游去处理（这体现了一种工程哲学：把"脏数据"交给最合适的地方去兜底）。

### 第 2 步：查找到对应的工具并执行

dsh 里执行工具前，会先通过 `ctx.tools.executionMode(...)` 判断这个调用
应该**串行还是并行**执行（我们稍后讲）。pi 里则是直接找到 `context.tools` 中
名字匹配的 `AgentTool`，调用它的 `execute`。

### 第 3 步：把结果封装成"user 角色消息"回传

工具执行完后，结果被封装成一条**工具结果消息**（dsh 的 `createToolResultMessage`），
它保留了 `callId`，让模型能对应上"这是上次那次调用的结果"。

```ts
// dsh packages/llm/llm/src/message.ts（节选，简化）
export function createToolResultMessage(input: ToolResultMessageInput): ToolResultMessage {
  // role: 'user'，content 里放一个 type:'tool-result' 的块
}
```

然后，这条结果消息被追加进会话。**下一轮请求时，模型就会看到：
"我说要跑 bash → 结果回来了，是 12345 行"。** 它据此决定下一步。

### 第 4 步：循环继续（或结束）

如果模型觉得任务完成，就不再输出 tool-call，而是直接输出一段最终文本。
推理循环检测到"这次没有工具调用"，就结束回合，把最终文本返回给用户。
**这个"检测有没有 tool-call → 决定继续还是结束"的逻辑，就是推理循环的核心判断。**
第 5 章我们详细展开。

## 3.4 串行还是并行？工具调度的学问

一个 assistant 消息可能**同时**包含多个 tool-call 块（模型一次想干好几件事）。
这时怎么执行？三个代码库都支持两种模式：

| 模式 | 含义 | 适用场景 |
|------|------|---------|
| **串行（sequential）** | 一个执行完，再执行下一个 | 有依赖关系：先查 A，再根据 A 查 B |
| **并行（parallel）** | 多个同时执行，互不干扰 | 无依赖：同时读多个文件 |

pi 的判定逻辑（`packages/agent/src/agent-loop.ts`）很简单：只要配置是串行，
**或者**这批调用里**有任何一个工具声明自己是串行**，就整体串行执行：

```ts
// pi packages/agent/src/agent-loop.ts（节选）
const hasSequentialToolCall = toolCalls.some(
  (tc) => currentContext.tools?.find((t) => t.name === tc.name)?.executionMode === "sequential",
);
if (config.toolExecution === "sequential" || hasSequentialToolCall) {
  return executeToolCallsSequential(...);   // 串行
}
return executeToolCallsParallel(...);       // 并行
```

dsh 的实现更复杂（`packages/core/agent-loop/src/tool-calls.ts`），
它引入了"**排他调用形成屏障（barrier）**、并行调用用有界滚动池"的调度器，
并保证"**结果按模型顺序提交**"——即使并行执行，返回给模型的顺序也要和
模型声明的顺序一致，否则模型会混淆。这是一个非常经典的工程细节：

> **并行执行，但按模型顺序返回。** 因为模型只会按它输出的顺序去理解工具结果。

```ts
// dsh packages/core/agent-loop/src/tool-calls.ts（节选，思路示意）
const mode = ctx.tools.executionMode(first.exec).kind
const group = mode === 'parallel' ? planned.slice(next) : [first]  // 并行成组 / 排他单独
const outcome = await runGroup(ctx, turn, step, group, mode, signal, acceptContext)
// runGroup 内部：并行执行，但按 callSeqs 顺序最终化结果
```

codex 同样支持并行工具调用（`tools/parallel.rs`），并且额外考虑了
"并行的工具之间可能互相冲突"的问题（比如两个工具同时改同一个文件），
用**冲突检测**来避免竞态。这类"生产级"考虑，我们到第 13 章再看。

## 3.5 工具的"说明书"为什么这么重要

也许你会想：工具不就是"一个函数"吗？值得花一章讲吗？
——**值得，因为模型只能通过说明书来"学会"你的工具。** 说明书的质量，
直接决定模型会不会正确调用它：

- `name` 要短而明确（`read_file` 优于 `rf2x`）；
- `description` 要写清楚"什么时候该用它、别用它做什么"；
- `parameters` 要写清楚类型、必填、默认值、取值范围。

一个真实的例子：codex 的 `apply_patch` 工具（`codex-rs/core/src/apply_patch.rs`），
它的 description 会明确告诉模型"这是一个基于统一 diff 格式的补丁工具，
适合修改文件，而不是整文件重写"。**模型读到这段描述，才会在"改一行代码"时
选择它，而不是把整个文件重写一遍。**

所以，当你写自己的 Agent 工具时，请把写 `description` 当作写"面向模型的文档"，
而不是给程序员看的注释。

## 3.6 本章小结

- **工具 = schema（说明书）+ execute（执行函数）**；
- 模型通过 tool-call 块声明"我要调用工具"，参数以 JSON 字符串形式传递；
- 工具结果被封装成 user 角色消息回传，作为下一轮模型的输入；
- 多个工具调用可串行可并行；并行执行也要按模型顺序返回结果；
- 说明书（description）质量决定模型能否正确使用工具。
