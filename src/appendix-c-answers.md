# 附录 C 练习参考答案

> 这里给出每章"动手练习"中**思考题**的参考答案，以及**实践类练习**的要点提示。
> 实践类练习没有唯一答案，这里提供"完成标准"与"易错点"。

## 第 1 章

1. **画骨架图**：完成标准——能画出"会话 → 组装 → 请求模型 → 判断输出 → 执行工具 →
   循环/返回"的闭环，并给每个环节写一句自己的解释。
2. **预览三库**：完成标准——三个目录都找到并浏览过。
3. **试运行**：没有 key 时跳过即可，不影响后续学习。

## 第 2 章

1. **查消息内容类型**：pi 的 `AssistantContentPart` 至少包括 text / thinking /
   toolCall / image 等；dsh 的 `ContentBlockMap` 至少包括 text / reasoning /
   image / tool-call / tool-result。**要点**：`toolCall` 块的 `arguments` 是
   **字符串**（模型输出是文本），需要解析。
2. **思考题：工具结果为什么用 `user` 角色？**
   - 从模型角度看，工具结果是"外部世界给它的输入"，和用户说话是同类来源；
   - 老模型 API 不认识 `tool` 角色，用 `user` 保证兼容性；
   - 为了区分"用户说的"和"工具返回的"，需要额外字段（如 `toolCallId`）做关联。

## 第 3 章

1. **读 read.ts**：完成标准——能说出 `name`、`description`、`parameters` 三个字段，
   以及 `execute` 用 `readFileSync`/`readTextFile` 读文件。
2. **写天气工具**：完成标准——定义好 schema（参数：城市名），execute 返回模拟数据。
3. **思考题：`arguments` 为什么是 JSON 字符串？**
   - 模型输出是文本流，天然产生字符串；
   - 框架可以统一"解析"这一步，且解析失败能宽容处理（见 dsh `parseArguments`）；
   - 若残缺 JSON 解析失败：不直接崩溃，保留原文交给下游报错；若是截断导致
     （`length`），最好**拒绝执行**并让模型重试（第 6 章）。

## 第 4 章

1. **读适配器**：完成标准——在 provider 文件里找到"统一消息 → 请求体"与
   "响应 → 统一事件流"两处转换。
2. **找 serialize**：dsh 的 `llm-deepseek/src/adapter.ts` 里有序列化逻辑。
3. **思考题：不用流式会怎样？**
   - **响应延迟**：模型要生成完整回答后才返回，用户/Agent 会"呆住"很久；
   - **提前感知**：Agent 无法在模型输出"我要调工具"时就准备工具执行，
     工具调用要等整段文本生成完，体验和效率都差；
   - 所以流式是 Agent 的必需品（工具调用、逐字 UI 都依赖它）。

## 第 5 章

1. **默写骨架**：完成标准——4 步：发请求、找工具调用、有则执行放回历史继续、
   无则返回。
2. **画状态机**：完成标准——含"等待输入 / 发请求 / 执行工具 / 完成 / 出错 / 取消"
   等状态与迁移。
3. **数 while**：pi 的 `agent-loop.ts` 里主循环是两个嵌套 `while`（外层回合、
   内层步骤），`streamAssistantResponse` 里还有 `for await` 流循环。

## 第 6 章

1. **改代码验证**：把 `if (toolCalls.length > 0)` 改成 `if (false)` 后，
   Agent 会"不调工具直接结束"——体会"工具调用是循环继续的动力"。
   记得改回来。
2. **读事件订阅方**：在 `packages/coding-agent/` 里找处理
   `message_update` / `tool_execution_start` 的代码，理解 UI 如何渲染。
3. **写假模型**：完成标准——假流返回"先 toolcall 后最终文本"，
   `newMessages` 应包含：用户消息、assistant(带工具)、工具结果、assistant(最终)。
4. **思考题：为什么 `length` 截断时拒绝执行工具？**
   - 截断意味着工具参数可能是**残缺 JSON**，解析虽宽容但内容不完整；
   - 执行不完整的调用很危险（比如 `rm -rf` 少了目标、`write` 写了半截内容）；
   - 所以宁可报错让模型重试，也不执行"半截"调用。

## 第 7 章

1. **读会话日志**：完成标准——找到 turn/start、user/message、assistant/chunk×N、
   assistant/message、tool/result、turn/end 等事件的顺序。
2. **打断它**：`steer()` 投到 `next-step`，模型下一轮会看到转向消息并调整方向。
3. **改瀑布**：完成标准——注册 `agent/pre-step` 监听器，返回加入额外上下文的
   `{ kind: 'enter', messages: [...claimed, extra] }`。
4. **思考题：为什么请求要"深冻结"？**
   - 请求必须**纯由会话日志派生**（可复现）；
   - 深冻结保证"请求一旦构造，谁都不能改"——否则插件在发出后改请求，
     "日志里记录的东西"和"实际发出的东西"就不一致，破坏"模型可见 ⟺ 可记录"。

## 第 8 章

1. **数保险**：完成标准——找到三个函数并各读 20 行，理解调用时机。
2. **画流程图**：完成标准——标出所有 `continue`（继续采样/压缩后继续）
   与 `break`（结束回合）分支。
3. **思考题：codex 内建压缩 vs dsh 维护阶段压缩？**
   - **codex 内建**：压缩时机精确（采样后立刻压缩继续），用户无感；缺点是循环
     更复杂、压缩与请求强耦合；
   - **dsh 维护阶段**：循环更清晰、压缩可替换；缺点是压缩时机可能与"模型请求前"
     不完全对齐，极端情况下可能需要"压缩后补一次请求"；
   - 没有绝对优劣，取决于产品对"无感续跑"的需求有多强。
4. **横向挑战**：无标准答案。常见合理回答：先模仿 pi 建立直觉，再用 dsh 的思路
   加会话日志与插件点，最后参考 codex 补重试/压缩/沙箱。

## 第 9 章

1. **翻译练习**：完成标准——能用"骨架三问"定位任意框架的循环入口、回合/步骤、
   保险清单。
2. **写对比笔记**：无标准答案，鼓励结合自己的项目场景。
3. **讨论题**：无标准答案。参考：持久化带来可恢复/可审计/可复现，但增加写日志
   开销与复杂度；对"跑一次就完"的短任务可能奢侈，对长期/多用户 Agent 服务
   几乎是必需品，且调试价值（可回放）难以替代。

## 第 10 章

1. **找 section**：完成标准——`grep -rn "systemPrompt.section"` 找到若干注册点，
   能区分静态文本与动态函数。
2. **测截断**：完成标准——找到 truncate 逻辑，能说出阈值与截断标记方式。
3. **思考题：压缩为什么需要重建世界状态？**
   - 模型没有记忆，只有每次的输入；
   - 压缩把历史变短后，如果不同步注入"当前文件系统/环境长什么样"，
     模型会"失忆"，无法理解后续工具结果（比如 `git status` 的输出）；
   - 所以压缩后要重新注入环境快照，让模型"虽见摘要，仍知现状"。

## 第 11 章

1. **看真实日志**：完成标准——找到一次模型请求对应的完整事件序列。
2. **试 deriveMessages**：`SURFACE_EVENT_TYPES` = user/message、assistant/message、
   tool/result。**不加 turn/start**——模型不需要看到管理事件，那是给审计用的，
   不是给模型看的。
3. **思考题：只存结果够吗？** 不够。没有日志就无法回答"为什么删了文件"，
   无法回放"模型当时看到了什么"，无法审计、无法做快照测试。

## 第 12 章

1. **读插件**：完成标准——能说出该包注册了哪些工具/事件/系统提示片段。
2. **写 SKILL.md**：完成标准——含 frontmatter（name、description），内容能指导
   模型完成任务，且能被 Agent 加载进上下文。
3. **连 MCP**：完成标准——MCP 服务器的工具出现在 Agent 工具清单里并能被调用。
4. **思考题：工具 vs 技能 vs 插件？**
   - **工具**：可调用的函数（执行能力）；
   - **技能**：给模型的文档（知识/流程）；
   - **插件**：改框架本身（能力注册、行为拦截）。
   - 选择：加"动作"用工具；加"知识"用技能；改"框架行为"用插件。

## 第 13 章

1. **查沙箱模式**：完成标准——列出 dsh 的沙箱模式（off/read-only/workspace-write/
   full 等）并说明各自场景。
2. **试审批**：完成标准——低风险自动放行、高风险弹审批，流程可观察。
3. **读超时**：完成标准——理解"工具超时后进程被终止、模型收到超时错误"。
4. **思考题：为什么沙箱模式要写进会话日志？**
   - "模型当时处于什么权限下"也是模型可见事实的一部分；
   - 回放时要能重建"当时的环境约束"，否则无法解释模型的行为（比如
     "它为什么不写那个文件"可能因为当时是只读模式）。

## 第 14 章

四个升级的完成标准：
1. **截断处理**：`finish_reason === "length"` 时拒绝执行工具、让模型重试；
2. **结果截断**：给工具结果设长度上限并附截断标记；
3. **错误重试**：最多 3 次、指数退避（`2^n * 500ms`）；
4. **日志会话**：每次 push 都记录时间/角色/摘要，跑完可回放"模型看到什么"。

易错点：截断处理要在"判断工具调用"之前；重试只对网络/临时错误，不要对
模型拒绝无限重试；日志要记录"摘要+关键字段"而不是可忽略的打印。

## 第 15 章

1. **纠错/补充**：鼓励以本地仓库为准核对代码细节（代码会演进）。
2. **写自己的 Agent**：完成标准——基于第 14 章代码 + 至少两个"保险"（如截断+日志）。
3. **选型练习**：无标准答案。参考框架：客服知识库 Agent 若"会话长、要审计、
   团队要扩展"，倾向 dsh 式（插件+日志）；若"要快速接多家模型做原型"，倾向
   pi 式；若"高危操作多、要强沙箱"，重视 codex 式安全能力。
